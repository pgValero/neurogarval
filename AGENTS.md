# AGENTS.md

Single-page marketing site for NeuroGarval (Spanish psychology practice). No package manager, no tests. There IS a minimal build step: Pages CMS edits YAML in `content/` (plus the type registry `.pages.yml`), and `scripts/build.py` substitutes `__file.path.field__` markers into the HTML templates and into the SEO/LLM text templates, writing `_site/`. Content is edited directly on `main` (each save triggers nothing); pressing **"Publicar cambios"** in Pages CMS runs `deploy_page.yml`, which first builds and validates the site and then publishes `_site/` to GitHub Pages.

**Language rule:** the repository (code, identifiers, comments, configuration, docs) is in **English**; everything the site owner reads in the browser or in the CMS is in **Spanish**. That means: the whole `content/*.yml` text, the page/SEO/JSON-LD texts, the Pages CMS `label`s and `description`s, and the public section anchors stay in Spanish, and they are never translated when the code around them is.

## Layout & deploy

- `src/index.html` — site template (HTML + a JSON-LD marker). Editable text is written as markers `__file.path.field__` (e.g. `__hero.badge__`, `__services.items.0.title__`) that `build.py` replaces from `content/*.yml` — do not hand-edit those; edit them in Pages CMS instead. The domain/base URL is read from `src/CNAME` during the build; the logo, `<html lang>`, SEO (title/description/keywords/canonical/geo.*), Open Graph + Twitter, the navigation menu labels and the structured-data texts are **not** hardcoded in the template either: they are markers into `content/clinic_info.yml` (read-only), e.g. `__clinic_info.seo.title__`, `__clinic_info.social.image__`, `__clinic_info.nav.home__`. Only structure stays here (the contact-card labels "Teléfono"/"WhatsApp"/…, the `&times;` close glyphs, classes, icon markup). The JSON-LD block is **generated** by `build.py` (`build_jsonld`, driven by the `clinic_info.structured_data` marker in `SPECIALS`): `WebSite`, the clinic as `["MedicalBusiness","Psychologist"]` (address, phone, email, `geo` parsed from the Maps embed in `contact.yml`, `areaServed` from `clinic_info.yml`, `sameAs` from Instagram + Maps, `hasOfferCatalog` from `services.yml`), a `Person` for the specialist (with the collegiate number from `specialist.yml`), a `FAQPage` from `faq.yml` and a `BlogPosting` per post in `blog.yml`. The site URL comes from `src/CNAME`; the other literal values in that graph come from the YAML (geo, currency, name/description/job title/`knowsAbout`/catalog name/credential category and the `@id` anchors live in `clinic_info.yml` → `site`/`schema`); in `build.py` only schema.org vocabulary (`@context`, `@type`) is left. Edit the YAML, never the JSON-LD. No embedded `<style>` and no bundler: the only inline `<script>` is the JSON-LD; the CSS is `src/styles.css` plus the Google Fonts and Bootstrap Icons CDNs. There are a few `style=""` attributes (button margins, Maps iframe border, `nowrap` of the modality line) and inline `onclick` handlers, so do not move them without also moving their function to `styles.css`/`script.js`. Do not introduce a framework or bundler. The build resolves **every** marker and fails if a field is missing (message names the field, the template and the reason). Cards and list items (services, modalities, process steps, blog posts and FAQ) are not repeated by hand per index: they are wrapped in `<!-- @foreach:file.path --> ... <!-- @endforeach:file.path -->` blocks and `build.py` generates them once per YAML element (see `expand_loops` in `build.py`). Inside the block, the `n` segment of a marker is the current element (`__services.items.n.title__` → `__services.items.0.title__`) and `__loop.index__`/`__loop.index0__` give the position (1-based/0-based).
- `src/signature.html` — standalone email signature template (not linked from the site; published as `_site/signature.html`); same marker system; the logo uses an absolute URL derived from `src/CNAME` (the build publishes `logo.svg` at the `_site/` root). The phone link uses the derived key `__common.contact.phone_tel__` (computed by `build.py` from `common.yml`, see `DERIVED_FIELDS`).
- `src/robots.txt`, `src/sitemap.xml`, `src/llms.txt`, `src/llms-full.txt` — SEO/LLM files that the build processes like the other templates (they are the keys of `TEMPLATES`) and publishes at the root of `_site/`: they use markers and `@foreach` loops like `src/index.html`, so there is **no** need to update them by hand when the content changes. `robots.txt` allows all crawlers, including AI ones. The sitemap lists the home page (with the `hero`/`specialist` images and the blog covers, always at the already-published WebP path) plus `llms.txt` and `llms-full.txt`. `llms.txt` (summary) and `llms-full.txt` (full content) are composed from the `content/*.yml`: services, modalities, process, FAQ and articles come from their lists, and `content/clinic_info.yml` → `llms` supplies what is not in any other file (section titles and session length). In the `.txt` files markers are inserted without HTML escaping and Markdown is converted to plain text; in the `.txt` loops multi-line items are separated by a blank line (single-line ones stay together, like in a list). The fixed prose in these files (headings, lead sentences, list labels) is **English**, while every marker that comes from `content/*.yml` keeps the Spanish text.
- `src/styles.css` — all site CSS, linked in `<head>` (Google Fonts and Bootstrap Icons come from a CDN, not from here).
- `src/script.js` — classic (non-module) script at end of `<body>`; **only** opens/closes the service, modality and blog modals and toggles the mobile menu. The full text of each card is already in the HTML (hidden `<div class="card-full" hidden>`, filled by `build.py` from `modal_content`/`article`) so search engines and AI crawlers read it without JavaScript; the script only copies that HTML into the modal (icons/title come from the same card, and the blog modal clones the card's `<img>` as cover). It injects no data: contact is written into the HTML by `build.py`. Inline `onclick` handlers rely on top-level functions staying global. Service modals are opened by id (`openServiceModal('neuro')`, which looks up `.service-card[data-service="neuro"]`) and modality/blog modals by index.
- `content/` — YAML edited via Pages CMS, **one file per page section** plus shared data: `hero.yml`, `services.yml`, `modalities.yml`, `process.yml`, `specialist.yml`, `blog.yml`, `faq.yml`, `contact.yml`, `footer.yml` (read-only in the CMS), `signature.yml` (signature copy), `common.yml` (read-only: the contact that repeats across hero, contact, footer and the signature) and `clinic_info.yml` (read-only: every fixed value of the site — `site` (name, `language`, `language_name`, `locale`, currency, logo, locality/region/`region_code`/country/`geo_position`; the domain comes from `src/CNAME` and `build.py` adds the derived `url` there), `seo` (title, description, keywords), `social` (Open Graph + Twitter), `nav` (menu labels), `ui` (close label), `llms` (section titles and session length for the LLM text files), `schema` (JSON-LD texts and `@id` anchors), `area_served` municipalities, `online_area`, `price_range` — plus the technical `structured_data` field whose marker expands the whole JSON-LD block). `build.py` loads every `content/*.yml` and fails if one is missing. The first segment of every marker must be a collection name of `.pages.yml` (and a file in `content/`).
- `media/` — source static resources (images, `favicon.svg`, `logo.svg`, `qr.svg` and PDFs `aviso_legal.pdf`/`tarjeta.pdf`; the build keeps the current public structure by publishing the favicon, the logo and the PDFs at the `_site/` root and the images under `media/` (`qr.svg` is not referenced by any template, but it is published anyway). Consultation-photo fields in the clinic modality are editable from Pages CMS and fall back to an icon while empty. The PNG/JPEG sources (`hero-image.png`, `blog-*.png`, `photo.jpeg`, `image.png`) stay in the repo: `prepare_media()` converts every one of them to WebP at build time and publishes **only** the WebP, so no PNG/JPEG copy reaches `_site/`. `image.png` is the single exception (`KEEP_AS_IS`): it stays in PNG on purpose because it is the `og:image` that WhatsApp, Facebook and other social networks read. If a PNG/JPEG from the CMS has no WebP sibling in the repo, the build still serves the converted WebP; you only need Pillow locally to verify.
- `.pages.yml` — Pages CMS config (`media` input/output, `components`, `collections`, `actions`) **and the build's type registry**: every field used in a marker must be declared here; `build.py` reads its `type` to decide how to render it (`rich-text` → Markdown, `image` → `media/` path, `component: icon` → icon HTML, plain strings/lists → escaped text). If a marker references a field that is not declared, the build fails. Comments are in English; every `label`, `description` and option text is in **Spanish**, because that is what the site owner reads in the CMS — do not translate them. `actions` (at the end of the file) declares the **"Publicar cambios"** button (`name: publish`) that triggers `.github/workflows/deploy_page.yml`. The long page fields are `rich-text` with `format: markdown`; titles, buttons and metadata stay simple fields. At the end there is a commented-out (disabled) future `content/posts/` collection for blog articles with their own pages.
- `scripts/build.py` — generator: loads `content/*.yml`, adds derived fields (`DERIVED_FIELDS`: `clinic_info.site.url`, `common.contact.phone_tel`, `signature.web_label`, `signature.web_url`), reads the type registry, substitutes every `__file.path.field__` marker in `src/index.html`, `src/signature.html` and in the SEO/LLM templates (`src/robots.txt`, `src/sitemap.xml`, `src/llms.txt`, `src/llms-full.txt`) — all of them are the keys of `TEMPLATES` —, expands the `@foreach` loop blocks over the YAML lists (`expand_loops`, `expand_loop`), writes contact data into the `.neuro-*` slots of the generated `index.html` (`fill_contact`), validates that every service `id` is present and unique (`validate_service_ids`), prepares the images (`prepare_media`): converts every PNG/JPEG of `media/` to WebP with Pillow and publishes only that version, and writes `_site/` with the current public structure (site files, favicon, logo and PDFs at its root, images under `media/`). Every template is published at the root of `_site/` with its own file name. Requires Python + PyYAML + Markdown + Pillow (Pillow only when there is a PNG/JPEG to convert). Rendered images are plain `<img>` tags with `width`/`height` (`image_html`/`img_tag`, sizes read from the file header by `image_size`/`webp_size`) plus `loading="lazy"`/`decoding="async"`, and `fetchpriority="high"` for the hero. `_site/` is gitignored (and is deleted and rebuilt from scratch on every run). Renderers that a field type cannot express live in `SPECIALS` (per template, exact route or glob pattern): `render_modalities` (joins the hero modality line with `·`, protecting the last item), `render_modality_content` (Markdown + optional consultation-photo gallery), `render_blog_thumb` (blog cover or fallback icon), `render_keywords` (joins the keyword list with commas), `render_social_image` (URL base + path), `render_site_logo` (absolute logo URL for the signature), `render_sitemap_image` (absolute published image path for the sitemap), `render_comma_list`/`render_plain`/`markdown_text` (plain text for the `.txt` templates, with a `"*"` catch-all) and `build_jsonld` (the whole JSON-LD graph).
- `scripts/check_site.sh` — check of the **published** site (called by `.github/workflows/check_site.yml`): reads the domain from `src/CNAME`, downloads the home page and verifies that it answers, that no `__x.y__` markers are left unresolved, that it has a `<title>`, the canonical URL, visible text and at least one image; and that `robots.txt`, `sitemap.xml`, `llms.txt`, `llms-full.txt`, `logo.svg` and `favicon.svg` answer. Run it with `bash scripts/check_site.sh` (it needs `curl`; it does not need Python).
- `CONTRIBUTING.md` — short guide (in English) for whoever arrives at the repo: how to install the dependencies, run the build and install the `prek` hooks. If you change the build or lint flow, update that file too.
- `.github/workflows/deploy_page.yml` — builds + publishes `_site/` on GitHub Pages. It runs **only via `workflow_dispatch`**: the Pages CMS **"Publicar cambios"** button (`.pages.yml` → `actions` → `publish`, on `main`) and the manual "Run workflow" button (fallback). Content commits pushed by Pages CMS land directly on `main` and trigger nothing; only this workflow deploys. The `build` job runs `python scripts/build.py` and then `prek run --config .pre-commit/.pre-commit-config.yaml --all-files` (since `_site/` is gitignored, it stages the result with `git add -f _site` so the lint covers the generated output) and uploads `_site/` as the Pages artifact; if it fails, the deploy job never runs and the live site keeps serving the previous version. The `deploy` job downloads that artifact with `actions/download-artifact` (`name: github-pages`, `path: _site`) and publishes it with `actions/deploy-pages`; from another branch it only builds and validates, it does not deploy (`if: github.ref == 'refs/heads/main'`). `concurrency: group pages` cancels a deployment if another one starts. Note: Pages CMS always sends a `payload` input (JSON) when it fires the event; workflows launched from the CMS must declare it in `on.workflow_dispatch.inputs` or GitHub rejects the event ("Unexpected inputs provided: [\"payload\"]").
- `.github/workflows/check_site.yml` — periodic check of the **published** site: daily `schedule` at 09:00 and 21:00 (`Europe/Madrid`) plus `workflow_dispatch`, with `permissions: contents: read`. It does a *sparse* checkout of `src` and `scripts` from `main` (without persisted credentials) and runs `bash scripts/check_site.sh`; if the published site does not answer or has broken, the run fails.
- `src/CNAME` — `neurogarval.es`; the build publishes it at the root of `_site/`; the host is GitHub Pages. **Repo Settings → Pages must be set to source "GitHub Actions"** (once). Pages CMS is used on **`main`** (`https://app.pagescms.org/pgValero/neurogarval/main`): content commits land directly on `main` and trigger nothing; only the **"Publicar cambios"** button deploys (via `deploy_page.yml`).

## Conventions

- **NEVER `git commit` or `git push` any change unless the user explicitly asks you to.** Always work in the working tree and leave the changes uncommitted. If a change deserves to be committed or published, propose it to the user and wait for confirmation before touching the history or the remote branch.
- **Language:** code, identifiers, comments, configuration and docs are in **English**; everything the site owner reads (page content, SEO/JSON-LD texts, Pages CMS `label`s and `description`s, public anchors, the public file names under `media/`) stays in **Spanish**. Commit messages are in Spanish too.
- The `content/*.yml` files keep exactly the format Pages CMS generates: **no YAML comments and no blank lines between fields or elements**. Do not add comments to those files; any hint for the editor belongs in the `description` of the corresponding field in `.pages.yml`. Blank lines inside Markdown block fields (`|`/`|-`) are part of the content and must be preserved.
- Contact data lives in `content/common.yml` → `build.py` writes the contact **directly into the HTML** (`.neuro-phone`, `.neuro-mail`, `.neuro-address`, and the tel/WhatsApp/mailto/Maps links) in every place it's needed, and into the generated `signature.html`. `common.yml` and `footer.yml` are read-only in Pages CMS; their address and footer text lists each require exactly two fixed items, so they cannot be added, removed, or reordered there. To change them, edit those files in the repository; the JSON-LD picks up the new phone/email/address automatically (it is generated from `common.yml` + `clinic_info.yml`). No JS is involved. Instagram lives in `content/contact.yml` (editable from the Contact section).
- Service cards call `openServiceModal('id')` — the id is the `id` field of each item in `content/services.yml` (`neuro`, `psico`, `rehab`), mandatory and editable in `.pages.yml` (lowercase, numbers and hyphens). Thanks to the `@foreach` loops, `src/index.html` takes that `id` as a marker (`__services.items.n.id__`), so `data-service`/`onclick` stay in sync on their own; there is no need to touch them when adding or removing services. Modality cards call `openModalityModal(index)`; the loop generates the index with `__loop.index0__`. Blog cards call `openBlogModal(index)` and open the article in a modal with its cover and the text of the `article` field. Modal copy comes from `build.py`'s `CONTEXT` (the loaded `content/*.yml`), not from card HTML. Consultation photos are configured per modality item in `content/modalities.yml` (`images`, each with `image`+`alt`); `modality_gallery` renders the photo grid inside the modality modal and, while a photo is empty, only its camera placeholder shows. The standalone gallery section no longer exists. The blog cards are real content edited in Pages CMS (`content/blog.yml`), not placeholder.
- Markers and types are the contract between the templates, `content/*.yml`, `.pages.yml` and `build.py`: every `__file.path.field__` must exist in the YAML **and** be declared in `.pages.yml`, or the build fails. The same applies to the markers inside an `@foreach` block (e.g. `__services.items.n.title__`): after expanding the loop they are resolved like the others; the `n` segment is only the element index and is not declared in `.pages.yml`. If a field changes type in `.pages.yml` (e.g. string → rich-text), update the marker's surrounding markup in the template (`<p>` → `<div class="markdown-content">`).
- Workflow security is checked by the zizmor hook, and the workflows are clean (there is no `zizmor.yml`: no audit is disabled). So: every `uses:` is pinned to a commit SHA with the version in a trailing comment (`uses: actions/checkout@<sha> # v4.4.0`), every job declares the least `permissions:` it needs (`contents: read` for the builds, `pages: write` + `id-token: write` only in the deploy job), `checkout` uses `persist-credentials: false` when the job does not need git credentials. There is no Dependabot, so the pins are refreshed by hand: `git ls-remote --tags https://github.com/<action>` and take the SHA of the newest `vX.Y.Z` of the major that is in use (zizmor fails on any tag/branch ref, so never leave a `@v4`).
- Do not write placeholder-shaped text (`__x.y__`) in HTML comments you want to keep verbatim: the build substitutes markers **everywhere**, including comments (those are used as editor hints and end up showing the resolved value).
- No hardcoded site values: the domain/base URL is read from `src/CNAME` during the build; every other literal that identifies this website (`<html lang>`, locale, currency, logo and image paths, SEO/Open Graph/Twitter tags, menu labels, `close_label`, and the JSON-LD texts) lives in `content/clinic_info.yml` and is **read-only** in Pages CMS — edit the YAML, not `src/index.html` or `build.py`. The templates and `build.py` only keep structure (markup, classes, icon names) and schema.org vocabulary (`@context`, `@type`). The only site text still in the templates is the contact-card labels ("Teléfono", "WhatsApp", "Instagram", "Email", "Dirección"), the `&times;` close glyphs and the logo's `alt="NeuroGarval"` in `src/signature.html`, which are part of the fixed markup. The files `src/robots.txt`, `src/sitemap.xml` and `src/llms*.txt` are marker templates: the domain comes from `src/CNAME` and the rest of the values from the YAML, they are not written by hand. Public URLs are frozen: the section anchors (`#inicio`, `#servicios`, …) and the public media file names (`media/aviso_legal.pdf`, `media/tarjeta.pdf`, …) stay as they are even though the sources are in English; renaming those would break live links.

## Verifying

- Build locally: `python scripts/build.py` (needs `pip install pyyaml markdown pillow`; without pip you can use `uv run --with pyyaml --with markdown --with pillow python scripts/build.py`). If Pillow is missing and there is a PNG/JPEG to convert, the build stops and names the dependency. After it finishes, open `_site/index.html` in a browser — never open `src/index.html` directly: its `.neuro-*` contact slots and markers are empty until `build.py` fills them (`_site/signature.html` is the generated signature).
- Lint: `prek run --config .pre-commit/.pre-commit-config.yaml --all-files` (HTMLHint, Stylelint, ESLint, Lychee, zizmor, ShellCheck, ruff check, ruff format and markdownlint-cli2; configs in `.pre-commit/.stylelintrc.json`, `.pre-commit/eslint.config.js`, `.pre-commit/ruff.toml` and `.pre-commit/.markdownlint-cli2.jsonc`). Lychee only lints `.html` and skips `tel:` links, the source-relative `src/favicon.svg` and the `__[a-z0-9_.]+__` template markers. zizmor only lints `.github/workflows/*.yml`; ShellCheck only lints `*.sh`; both ruff hooks only lint `.py` (with the curated rule list of `.pre-commit/ruff.toml`, which excludes `E501` because of the single-line SVG path data in `build.py`); markdownlint-cli2 lints `*.md` with the default rule set minus `MD013` (the docs use long prose lines on purpose). Remember that `prek` only lints git-tracked files, so to lint the generated site you must `git add -f _site` first (that's what the CI does).
- Published site: `bash scripts/check_site.sh` (needs `curl` only) is the same check the scheduled `check_site.yml` runs against the live domain.
- Check section by section (`#inicio`, `#servicios`, `#modalidades`, `#proceso`, `#especialista`, `#blog`, `#faq`, `#contacto`), a service modal, each modality modal, each blog modal, and the mobile menu.
- `src/index.html` (~380 lines), `src/styles.css` (~940 lines), `src/script.js` (~85 lines), `scripts/build.py` (~1,235 lines, formatted with `ruff format`); prefer targeted `Edit` calls over `Write`.
