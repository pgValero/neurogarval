# AGENTS.md

Single-page marketing site for NeuroGarval (Spanish psychology practice). No package manager, no tests. There IS a minimal build step: Pages CMS edits YAML in `content/` (plus the type registry `.pages.yml`), and `scripts/build.py` substitutes `__archivo.ruta.campo__` markers into the HTML templates and into the SEO/LLM text templates, writing `_site/`. Content is edited on `develop`; a PR `develop → main` (auto-merged with rebase) is what puts it live, because the push to `main` is what builds and deploys `_site/` to GitHub Pages.

## Layout & deploy

- `src/index.html` — site template (HTML + a JSON-LD marker). Editable text is written as markers `__archivo.ruta.campo__` (p. ej. `__hero.badge__`, `__servicios.items.0.title__`) that `build.py` replaces from `content/*.yml` — do not hand-edit those; edit them in Pages CMS instead. The domain/base URL is read from `src/CNAME` during the build; the logo, `<html lang>`, SEO (title/description/keywords/canonical/geo.*), Open Graph + Twitter, the navigation menu labels and the structured-data texts are **not** hardcoded in the template either: they are markers into `content/clinic_info.yml` (read-only), e.g. `__clinic_info.seo.title__`, `__clinic_info.social.image__`, `__clinic_info.nav.inicio__`. Only structure stays here (the contact-card labels "Teléfono"/"WhatsApp"/…, the `&times;` close glyphs, classes, icon markup). The JSON-LD block is **generated** by `build.py` (`build_jsonld`, driven by the `clinic_info.datos_estructurados` marker in `SPECIALS`): `WebSite`, the clinic as `["MedicalBusiness","Psychologist"]` (address, phone, email, `geo` parsed from the Maps embed in `contacto.yml`, `areaServed` from `clinic_info.yml`, `sameAs` from Instagram + Maps, `hasOfferCatalog` from `servicios.yml`), a `Person` for the specialist (with the collegiate number from `especialista.yml`), a `FAQPage` from `faq.yml` and a `BlogPosting` per post in `blog.yml`. The site URL comes from `src/CNAME`; the other literal values in that graph come from the YAML (geo, currency, name/description/job title/`knowsAbout`/catalog name/credential category and the `@id` anchors live in `clinic_info.yml` → `site`/`schema`); in `build.py` only schema.org vocabulary (`@context`, `@type`) is left. Edit the YAML, never the JSON-LD. No `<style>` embebido ni bundler: el único `<script>` en línea es el JSON-LD; el CSS es `src/styles.css` más las CDN de Google Fonts y Bootstrap Icons. Sí hay unos pocos `style=""` (márgenes de los botones, borde del iframe de Maps, `nowrap` de la línea de modalidades) y `onclick` inline, así que no los muevas de sitio sin pasar también su función a `styles.css`/`script.js`. Do not introduce a framework or bundler. The build resolves **every** marker and fails if a field is missing (message names the field, the template and the reason). Las tarjetas e ítems de las listas (servicios, modalidades, pasos del proceso, posts del blog y FAQ) no se repiten a mano por índice: van envueltas en bloques `<!-- @foreach:archivo.ruta --> ... <!-- @endforeach:archivo.ruta -->` y `build.py` las genera una vez por elemento del YAML (ver `expand_loops` en `build.py`). Dentro del bloque, el segmento `n` del marcador es el elemento actual (`__servicios.items.n.title__` → `__servicios.items.0.title__`) y `__loop.index__`/`__loop.index0__` dan la posición (1-based/0-based).
- `src/firma.html` — standalone email signature template (not linked from the site); same marker system; the logo uses an absolute URL derived from `src/CNAME` (the build publishes `logo.svg` at the `_site/` root). The phone link uses the derived key `__common.contact.phone_tel__` (computed by `build.py` from `common.yml`, see `DERIVED_FIELDS`).
- `src/robots.txt`, `src/sitemap.xml`, `src/llms.txt`, `src/llms-full.txt` — ficheros SEO/LLM que el build procesa como el resto de plantillas (`TEMPLATES`) y publica en la raíz de `_site/`: usan marcadores y bucles `@foreach` como `src/index.html`, así que **no** hay que actualizarlos a mano cuando cambia el contenido. `robots.txt` permite todos los rastreadores, incluidos los de IA. El sitemap lista la portada (con las imágenes de `hero`/`especialista` y las portadas del blog, siempre en la ruta WebP ya publicada) y además `llms.txt` y `llms-full.txt`. `llms.txt` (resumen) y `llms-full.txt` (contenido completo) se componen con los `content/*.yml`: servicios, modalidades, proceso, FAQ y artículos salen de sus listas, y `content/clinic_info.yml` → `llms` aporta lo que no está en ninguna otra parte (títulos de sección y duración de la sesión). En los `.txt` los marcadores se insertan sin escapes de HTML y el Markdown se pasa a texto plano; en los bucles de los `.txt` los elementos multilínea se separan con una línea en blanco (los de una sola línea van juntos, como en una lista).
- `src/styles.css` — all site CSS, linked in `<head>` (Google Fonts y Bootstrap Icons vienen de CDN, no de aquí).
- `src/script.js` — classic (non-module) script at end of `<body>`; **only** opens/closes the service, modality and blog modals and toggles the mobile menu. The full text of each card is already in the HTML (hidden `<div class="card-full" hidden>`, filled by `build.py` from `modal_content`/`article`) so search engines and AI crawlers read it without JavaScript; the script only copies that HTML into the modal (icons/title come from the same card, and the blog modal clones the card's `<img>` as cover). It injects no data: contact is written into the HTML by `build.py`. Inline `onclick` handlers rely on top-level functions staying global. Service modals are opened by id (`openServiceModal('neuro')`, which looks up `.service-card[data-service="neuro"]`) and modality/blog modals by index.
- `content/` — YAML edited via Pages CMS, **one file per page section** plus shared data: `hero.yml`, `servicios.yml`, `modalidades.yml`, `proceso.yml`, `especialista.yml`, `blog.yml`, `faq.yml`, `contacto.yml`, `footer.yml` (read-only in the CMS), `firma.yml` (signature copy), `common.yml` (read-only: the contact that repeats across hero, contact, footer and the signature) and `clinic_info.yml` (read-only: every fixed value of the site — `site` (name, `language`, `language_name`, `locale`, currency, logo, locality/region/`region_code`/country/`geo_position`; el dominio sale de `src/CNAME` y `build.py` añade ahí la `url` derivada), `seo` (title, description, keywords), `social` (Open Graph + Twitter), `nav` (menu labels), `ui` (close label), `llms` (section titles and session length for the LLM text files), `schema` (JSON-LD texts and `@id` anchors), `area_served` municipalities, `online_area`, `price_range` — plus the technical `datos_estructurados` field whose marker expands the whole JSON-LD block). `build.py` loads every `content/*.yml` and fails if one is missing. The first segment of every marker must be a collection name of `.pages.yml` (and a file in `content/`).
- `media/` — source static resources (images, `favicon.svg`, `logo.svg`, `qr.svg` and PDFs `aviso_legal.pdf`/`tarjeta.pdf`; the build keeps the current public structure by publishing the favicon, the logo and the PDFs at the `_site/` root and the images under `media/` (`qr.svg` no lo referencia ninguna plantilla, pero se publica igualmente). Consultation-photo fields in the clinic modality are editable from Pages CMS and fall back to an icon while empty. The PNG/JPEG sources (`hero-image.png`, `blog-*.png`, `photo.jpeg`, `image.png`) stay in the repo: `prepare_media()` converts every one of them to WebP at build time and publishes **only** the WebP, so no PNG/JPEG copy reaches `_site/`. `image.png` is the single exception (`KEEP_AS_IS`): it stays in PNG on purpose because it is the `og:image` that WhatsApp, Facebook and other social networks read. If a PNG/JPEG from the CMS has no WebP sibling in the repo, the build still serves the converted WebP; you only need Pillow locally to verify.
- `.pages.yml` — Pages CMS config (`media` input/output, `components`, `collections`, `actions`) **and the build's type registry**: every field used in a marker must be declared here; `build.py` reads its `type` to decide how to render it (`rich-text` → Markdown, `image` → `media/` path, `component: icono` → icon HTML, plain strings/lists → escaped text). If a marker references a field that is not declared, the build fails. Commented in Spanish. `actions` (al final del fichero) declara el botón **"Publicar cambios"** (`name: publicar`) que dispara `.github/workflows/create_pr.yml`. Los campos largos de la página son `rich-text` con `format: markdown`; los títulos, botones y metadatos siguen siendo campos simples. Al final queda comentado (desactivado) el futuro `content/posts/` para artículos del blog con páginas propias.
- `scripts/build.py` — generator: loads `content/*.yml`, adds derived fields (`DERIVED_FIELDS`: `clinic_info.site.url`, `common.contact.phone_tel`, `firma.web_label`, `firma.web_url`), reads the type registry, substitutes every `__archivo.ruta.campo__` marker in `src/index.html`, `src/firma.html` and in the SEO/LLM templates (`src/robots.txt`, `src/sitemap.xml`, `src/llms.txt`, `src/llms-full.txt`) — all of them are the keys of `TEMPLATES` —, expands the `@foreach` loop blocks over the YAML lists (`expand_loops`, `expand_loop`), writes contact data into the `.neuro-*` slots of the generated `index.html` (`fill_contact`), validates that every service `id` is present and unique (`validate_service_ids`), prepares the images (`prepare_media`): converts every PNG/JPEG of `media/` to WebP with Pillow and publishes only that version, and writes `_site/` with the current public structure (site files, favicon, logo and PDFs at its root, images under `media/`). Requires Python + PyYAML + Markdown + Pillow (Pillow only when there is a PNG/JPEG to convert). Rendered images are plain `<img>` tags with `width`/`height` (`image_html`/`img_tag`, sizes read from the file header by `image_size`/`webp_size`) plus `loading="lazy"`/`decoding="async"`, and `fetchpriority="high"` for the hero. `_site/` is gitignored (and is deleted and rebuilt from scratch on every run). Renderers that a field type cannot express live in `SPECIALS` (per template, exact route or glob pattern): `render_modalities` (joins the hero modality line with `·`, protecting the last item), `render_modality_content` (Markdown + optional consultation-photo gallery), `render_blog_thumb` (blog cover or fallback icon), `render_keywords` (joins the keyword list with commas), `render_social_image` (URL base + path), `render_site_logo` (absolute logo URL for the signature), `render_sitemap_image` (absolute published image path for the sitemap), `render_comma_list`/`render_plain`/`markdown_text` (plain text for the `.txt` templates, with a `"*"` catch-all) and `build_jsonld` (the whole JSON-LD graph).
- `scripts/check_site.sh` — comprobación del sitio **publicado** (lo llama `.github/workflows/check_site.yml`): lee el dominio de `src/CNAME`, se baja la portada y verifica que responde, que no le quedan marcadores `__x.y__` sin resolver, que tiene `<title>`, la URL canónica, texto visible y al menos una imagen; y que `robots.txt`, `sitemap.xml`, `llms.txt`, `llms-full.txt`, `logo.svg` y `favicon.svg` responden. Se ejecuta con `bash scripts/check_site.sh` (necesita `curl`; no necesita Python).
- `CONTRIBUTING.md` — guía breve (en español) para quien llega al repo: cómo instalar dependencias, ejecutar el build e instalar los hooks de `prek`. Si cambias el flujo de build o de lint, actualiza también ese fichero.
- `.github/workflows/build_validation.yml` — workflow **reutilizable** (`workflow_call`) de build + validación: se ejecuta en **cada pull request contra `main`** y también la invoca `deploy_page.yml` antes de desplegar. Hace `python scripts/build.py` y luego `prek run --config .pre-commit/.pre-commit-config.yaml --all-files` (mismo criterio que el despliegue); como `_site/` está gitignored, indexa el resultado con `git add -f _site` para que el lint cubra lo generado. Acepta el input booleano `upload_artifact` (por defecto `false`): solo `deploy_page.yml` lo activa, y es lo que sube `_site/` como artefacto de Pages; en las PR el paso se omite (`if: inputs.upload_artifact`). Es el status check que la protección de rama de `main` exige como obligatorio: si falla, la PR no se mergea ni la toca el auto-merge. Ojo: el check se llama **`Build Validation / build-validation`**, no `checks`.
- `.github/workflows/create_pr.yml` — **botón "Publicar cambios" de Pages CMS** (`.pages.yml` → `actions` → `publicar`; se lanza con `workflow_dispatch` solo desde `develop`): si `develop` tiene cambios respecto a `main`, crea (o reutiliza) la PR `develop → main` y la marca para **auto-merge con rebase**; GitHub la mergea sola en cuanto pasan los checks obligatorios. Si no hay cambios, no hace nada. Ojo: Pages CMS envía siempre un input `payload` (JSON) al disparar el evento; los workflows lanzados desde el CMS deben declararlo en `on.workflow_dispatch.inputs` o GitHub rechaza el evento ("Unexpected inputs provided: [\"payload\"]"). También define `GH_TOKEN: ${{ github.token }}` en el job: `gh` no se autentica en Actions sin esa variable de entorno explícita.
- `.github/workflows/deploy_page.yml` — build + publica `_site/` en GitHub Pages. Se lanza **automáticamente al hacer push a `main`** (al mergear la PR de publicación) y también a mano con "Run workflow" (fallback). El job `build` reutiliza `build_validation.yml` (`uses:` + `with: upload_artifact: true`), que deja `_site/` en el artefacto de Pages, y el job `deploy` lo descarga y publica; desde otra rama solo se construye y valida, no se despliega (`if: github.ref == 'refs/heads/main'`). `concurrency: group pages` cancela un despliegue si arranca otro.
- `.github/workflows/check_site.yml` — comprobación periódica del sitio **publicado**: `schedule` diario a las 09:00 y 21:00 (`Europe/Madrid`) más `workflow_dispatch`, con `permissions: contents: read`. Hace un checkout *sparse* de `src` y `scripts` de `main` (sin credenciales persistentes) y ejecuta `bash scripts/check_site.sh`; si el sitio publicado no responde o ha quedado roto, falla el run.
- `src/CNAME` — `neurogarval.es`; el build lo publica en la raíz de `_site/`; host is GitHub Pages. **Repo Settings → Pages must be set to source "GitHub Actions"** (once). **Protección de rama en `main`** (Settings → Branches, una vez): require PR, status check `Build Validation / build-validation` obligatorio (`create_pr.yml` + auto-merge, y `deploy_page.yml` se auto-publican). Pages CMS se usa sobre **`develop`** (`https://app.pagescms.org/pgValero/neurogarval/develop`); `main` no recibe empujes directos. La primera publicación migra `main` al sistema nuevo (hoy `main` tiene aún el sitio antiguo en la raíz; se hace una PR inicial `develop → main` a mano, antes de activar la protección, porque `main` aún no tiene los workflows).

## Conventions

- **NUNCA JAMÁS hagas `git commit` ni `git push` de ningún cambio salvo que el usuario te lo pida explícitamente.** Trabaja siempre en el working tree y deja los cambios sin commitear. Si un cambio merece commitearse o publicarse, propónselo al usuario y espera su confirmación antes de tocar el historial o la rama remota.
- All user-facing copy is **Spanish**. Write edits in Spanish; commit messages are in Spanish too.
- Los archivos `content/*.yml` mantienen exactamente el formato que genera Pages CMS: **sin comentarios YAML ni líneas vacías entre campos o elementos**. No añadas comentarios en esos archivos; cualquier indicación para el editor debe estar en la `description` del campo correspondiente de `.pages.yml`. Las líneas vacías dentro de campos de bloque Markdown (`|`/`|-`) forman parte del contenido y deben conservarse.
- Contact data lives in `content/common.yml` → `build.py` writes the contact **directly into the HTML** (`.neuro-phone`, `.neuro-mail`, `.neuro-address`, and tel/WhatsApp/mailto/Maps links) in every place it's needed, and into the generated `firma.html`. `common.yml` and `footer.yml` are read-only in Pages CMS; their address and footer text lists each require exactly two fixed items, so they cannot be added, removed, or reordered there. To change them, edit those files in the repository; the JSON-LD picks up the new phone/email/address automatically (it is generated from `common.yml` + `clinic_info.yml`). No JS is involved. Instagram lives in `content/contacto.yml` (editable from the Contact section).
- Service cards call `openServiceModal('id')` — the id is the `id` field of each item in `content/servicios.yml` (`neuro`, `psico`, `rehab`), obligatorio y editable en `.pages.yml` (minúsculas, números y guiones). Gracias a los bucles `@foreach`, `src/index.html` toma ese `id` como marcador (`__servicios.items.n.id__`), así que `data-service`/`onclick` quedan sincronizados solos; no hace falta tocarlos al añadir o quitar servicios. Modality cards call `openModalityModal(index)`; el índice lo genera el bucle con `__loop.index0__`. Blog cards call `openBlogModal(index)` y abren el artículo en un modal con su portada y el texto del campo `article`. Modal copy comes from `build.py`'s `CONTEXT` (the loaded `content/*.yml`), not from card HTML. Consultation photos are configured per modality item in `content/modalidades.yml` (`images`, each with `image`+`alt`); `modality_gallery` renders the photo grid inside the modality modal and, while a photo is empty, only its camera placeholder shows. The standalone gallery section no longer exists. The blog cards are real content edited in Pages CMS (`content/blog.yml`), not placeholder.
- Markers and types are the contract between the templates, `content/*.yml`, `.pages.yml` and `build.py`: every `__archivo.ruta.campo__` must exist in the YAML **and** be declared in `.pages.yml`, or the build fails. Lo mismo aplica a los marcadores de dentro de un bloque `@foreach` (p. ej. `__servicios.items.n.title__`): después de expandir el bucle se resuelven como los demás; el segmento `n` es solo el índice del elemento y no se declara en `.pages.yml`. If a field changes type in `.pages.yml` (p. ej. string → rich-text), update the marker's surrounding markup in the template (`<p>` → `<div class="markdown-content">`).
- Do not write placeholder-shaped text (`__x.y__`) in HTML comments you want to keep verbatim: the build substitutes markers **everywhere**, including comments (those are used as editor hints and end up showing the resolved value).
- No hardcoded site values: the domain/base URL is read from `src/CNAME` during the build; every other literal that identifies this website (`<html lang>`, locale, currency, logo and image paths, SEO/Open Graph/Twitter tags, menu labels, `close_label`, and the JSON-LD texts) lives in `content/clinic_info.yml` and is **read-only** in Pages CMS — edit the YAML, not `src/index.html` or `build.py`. The templates and `build.py` only keep structure (markup, classes, icon names) and schema.org vocabulary (`@context`, `@type`). The only site text still in the templates is the contact-card labels ("Teléfono", "WhatsApp", "Instagram", "Email", "Dirección"), the `&times;` close glyphs and the logo's `alt="NeuroGarval"` in `src/firma.html`, which are part of the fixed markup. Los ficheros `src/robots.txt`, `src/sitemap.xml` y `src/llms*.txt` son plantillas con marcadores: el dominio sale de `src/CNAME` y el resto de valores de los YAML, no se escriben a mano.

## Verifying

- Build locally: `python scripts/build.py` (needs `pip install pyyaml markdown pillow`; sin pip se puede usar `uv run --with pyyaml --with markdown --with pillow python scripts/build.py`). Si falta Pillow y hay alguna imagen PNG/JPEG que convertir, el build se detiene indicando la dependencia. After it finishes, open `_site/index.html` in a browser — never open `src/index.html` directly: its `.neuro-*` contact slots and markers are empty until `build.py` fills them (`_site/firma.html` is the generated signature).
- Lint: `prek run --config .pre-commit/.pre-commit-config.yaml --all-files` (HTMLHint, Stylelint, ESLint, Lychee; configs in `.pre-commit/.stylelintrc.json` and `.pre-commit/eslint.config.js`). Lychee only lints `.html` and skips `tel:` links, the source-relative `src/favicon.svg` and the `__[a-z0-9_.]+__` template markers. Remember that `prek` only lints git-tracked files, so to lint the generated site you must `git add -f _site` first (that's what the CI does).
- Published site: `bash scripts/check_site.sh` (needs `curl` only) is the same check the scheduled `check_site.yml` runs against the live domain.
- Check section by section (`#inicio`, `#servicios`, `#modalidades`, `#proceso`, `#especialista`, `#blog`, `#faq`, `#contacto`), a service modal, each modality modal, each blog modal, and the mobile menu.
- `src/index.html` (~380 lines), `src/styles.css` (~940 lines), `src/script.js` (~85 lines), `scripts/build.py` (~1180 lines); prefer targeted `Edit` calls over `Write`.
