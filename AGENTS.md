# AGENTS.md

Single-page marketing site for NeuroGarval (Spanish psychology practice). No package manager, no tests. There IS a minimal build step: Pages CMS edits YAML in `content/` (plus the type registry `.pages.yml`), and `build.py` substitutes `__archivo.ruta.campo__` markers into the HTML templates.

## Layout & deploy

- `src/index.html` — site template (HTML + a JSON-LD marker). Editable text is written as markers `__archivo.ruta.campo__` (p. ej. `__hero.badge__`, `__servicios.items.0.title__`) that `build.py` replaces from `content/*.yml` — do not hand-edit those; edit them in Pages CMS instead. Domain/base URLs, logo, `<html lang>`, SEO (title/description/keywords/canonical/geo.*), Open Graph + Twitter, the navigation menu labels and the structured-data texts are **not** hardcoded in the template either: they are markers into `content/clinic_info.yml` (read-only), e.g. `__clinic_info.seo.title__`, `__clinic_info.site.url__`, `__clinic_info.social.image__`, `__clinic_info.nav.inicio__`. Only structure stays here (the contact-card labels "Teléfono"/"WhatsApp"/…, the `&times;` close glyphs, classes, icon markup). The JSON-LD block is **generated** by `build.py` (`build_jsonld`, driven by the `clinic_info.datos_estructurados` marker in `SPECIALS`): `WebSite`, the clinic as `["MedicalBusiness","Psychologist"]` (address, phone, email, `geo` parsed from the Maps embed in `contacto.yml`, `areaServed` from `clinic_info.yml`, `sameAs` from Instagram + Maps, `hasOfferCatalog` from `servicios.yml`), a `Person` for the specialist (with the collegiate number from `especialista.yml`), a `FAQPage` from `faq.yml` and a `BlogPosting` per post in `blog.yml`. Every literal value in that graph comes from the YAML (site URL, geo, currency, name/description/job title/`knowsAbout`/catalog name/credential category and the `@id` anchors live in `clinic_info.yml` → `site`/`schema`); in `build.py` only schema.org vocabulary (`@context`, `@type`) is left. Edit the YAML, never the JSON-LD. No inline `<style>`/`<script>`; do not introduce a framework or bundler. The build resolves **every** marker and fails if a field is missing (message names the field, the template and the reason). Las tarjetas e ítems de las listas (servicios, modalidades, pasos del proceso, posts del blog y FAQ) no se repiten a mano por índice: van envueltas en bloques `<!-- @foreach:archivo.ruta --> ... <!-- @endforeach:archivo.ruta -->` y `build.py` las genera una vez por elemento del YAML (ver `expand_loops` en `build.py`). Dentro del bloque, el segmento `n` del marcador es el elemento actual (`__servicios.items.n.title__` → `__servicios.items.0.title__`) y `__loop.index__`/`__loop.index0__` dan la posición (1-based/0-based).
- `src/firma.html` — standalone email signature template (not linked from the site); same marker system; the fixed logo uses an absolute `https://neurogarval.es/logo.svg` URL (the build publishes `logo.svg` at the `_site/` root). The phone link uses the derived key `__common.contact.phone_tel__` (computed by `build.py` from `common.yml`, see `DERIVED_FIELDS`).
- `src/robots.txt`, `src/sitemap.xml`, `src/llms.txt`, `src/llms-full.txt` — ficheros SEO/LLM **fijos** (no usan marcadores) que el build copia a la raíz de `_site/` (`STATIC_FILES`). `robots.txt` permite todos los rastreadores, incluidos los de IA. `llms.txt` (resumen) y `llms-full.txt` (contenido completo) duplican a mano el contenido de `content/*.yml`: si cambian servicios, FAQ, artículos o contacto, actualízalos también.
- `src/styles.css` — all site CSS, linked in `<head>`.
- `src/script.js` — classic (non-module) script at end of `<body>`; **only** opens/closes the service, modality and blog modals and toggles the mobile menu. The full text of each card is already in the HTML (hidden `<div class="card-full" hidden>`, filled by `build.py` from `modal_content`/`article`) so search engines and AI crawlers read it without JavaScript; the script only copies that HTML into the modal (icons/title come from the same card). It injects no data: contact is written into the HTML by `build.py`. Inline `onclick` handlers rely on top-level functions staying global. Service modals are opened by id (`openServiceModal('neuro')`, which looks up `.service-card[data-service="neuro"]`) and modality/blog modals by index.
- `content/` — YAML edited via Pages CMS, **one file per page section** plus shared data: `hero.yml`, `servicios.yml`, `modalidades.yml`, `proceso.yml`, `especialista.yml`, `blog.yml`, `faq.yml`, `contacto.yml`, `footer.yml` (read-only in the CMS), `firma.yml` (signature copy), `common.yml` (read-only: the contact that repeats across hero, contact, footer and the signature) and `clinic_info.yml` (read-only: every fixed value of the site — `site` (domain, name, `lang`, `locale`, currency, logo, locality/region/country/coordinates), `seo` (title, description, keywords), `social` (Open Graph + Twitter), `nav` (menu labels), `ui` (close label), `schema` (JSON-LD texts and `@id` anchors), `area_served` municipalities, `online_area`, `price_range` — plus the technical `datos_estructurados` field whose marker expands the whole JSON-LD block). `build.py` loads every `content/*.yml` and fails if one is missing. The first segment of every marker must be a collection name of `.pages.yml` (and a file in `content/`).
- `media/` — source static resources (images, `favicon.svg`, `logo.svg` and PDFs `aviso_legal.pdf`/`tarjeta.pdf`); the build keeps the current public structure by publishing the favicon, the logo and the PDFs at the `_site/` root and the images under `media/`. Consultation-photo fields in the clinic modality are editable from Pages CMS and fall back to an icon while empty. Images are published in WebP only (there are no PNG/JPEG copies in `media/`). `media/image.png` stays in PNG on purpose: it is the `og:image` that WhatsApp, Facebook and other social networks read. To add or replace an image, prefer WebP (`uv run --with pillow python -c "from PIL import Image; Image.open('media/x.png').save('media/x.webp','WEBP',quality=82)"`); if a PNG/JPEG from the CMS has no WebP sibling, the build serves the original without a `<picture>`.
- `.pages.yml` — Pages CMS config (collections, fields, media paths) **and the build's type registry**: every field used in a marker must be declared here; `build.py` reads its `type` to decide how to render it (`rich-text` → Markdown, `image` → `media/` path, `component: icono` → icon HTML, plain strings/lists → escaped text). If a marker references a field that is not declared, the build fails. Commented in Spanish. Los campos largos de la página son `rich-text` con `format: markdown`; los títulos, botones y metadatos siguen siendo campos simples.
- `build.py` — generator: loads `content/*.yml`, adds derived fields (`DERIVED_FIELDS`, p. ej. `common.contact.phone_tel`), reads the type registry, substitutes every `__archivo.ruta.campo__` marker in `src/index.html` and `src/firma.html`, expands the `@foreach` loop blocks over the YAML lists (`expand_loops`, `expand_loop`), writes contact data into the `.neuro-*` slots of the generated `index.html` (`fill_contact`), validates that every service `id` is present and unique (`validate_service_ids`), prepares the images (`prepare_media`): converts every PNG/JPEG of `media/` to WebP with Pillow and publishes only that version, and writes `_site/` with the current public structure (site files, favicon, logo and PDFs at its root, images under `media/`). Requires Python + PyYAML + Markdown + Pillow. Rendered images are plain `<img>` tags with `width`/`height` (`image_html`/`img_tag`, sizes read from the file header by `image_size`/`webp_size`) plus `loading="lazy"`/`decoding="async"`, and `fetchpriority="high"` for the hero. `_site/` is gitignored. Renderers that a field type cannot express live in `SPECIALS` (per template, exact route or glob pattern): `render_keywords` (joins the keyword list with commas), `render_social_image` (absolute `site.url` + path) and `build_jsonld` (the whole JSON-LD graph).
- `.github/workflows/checks.yml` — PR checks: runs on **every pull request against `main`** (build.py + `prek run --all-files`, mismo criterio que el despliegue). Su resultado es el status check **`checks`**, que la protección de rama de `main` exige como obligatorio: si falla, la PR no se mergea.
- `.github/workflows/publicar.yml` — **botón "Publicar cambios" de Pages CMS** (`.pages.yml` → `actions` → `publicar`; se lanza con `workflow_dispatch` solo desde `develop`): si `develop` tiene cambios respecto a `main`, crea (o reutiliza) la PR `develop → main` y la marca para **auto-merge con rebase**; GitHub la mergea sola en cuanto pasan los checks obligatorios. Si no hay cambios, no hace nada. Ojo: Pages CMS envía siempre un input `payload` (JSON) al disparar el evento; los workflows lanzados desde el CMS deben declararlo en `on.workflow_dispatch.inputs` o GitHub rechaza el evento ("Unexpected inputs provided: [\"payload\"]"). También define `GH_TOKEN: ${{ github.token }}` en el job: `gh` no se autentica en Actions sin esa variable de entorno explícita.
- `.github/workflows/deploy.yml` — build + publica `_site/` en GitHub Pages. Se lanza **automáticamente al hacer push a `main`** (al mergear la PR de publicación) y también a mano con "Run workflow" (fallback). Desde otra rama solo construye y valida, no despliega (`if: github.ref == 'refs/heads/main'`).
- `CNAME` — `neurogarval.es`; host is GitHub Pages. **Repo Settings → Pages must be set to source "GitHub Actions"** (once). **Protección de rama en `main`** (Settings → Branches, una vez): require PR, status check `checks` obligatorio (`publicar.yml` + auto-merge, y `deploy.yml` se auto-publican). Pages CMS se usa sobre **`develop`** (`https://app.pagescms.org/pgValero/neurogarval/develop`); `main` no recibe empujes directos. La primera publicación migra `main` al sistema nuevo (hoy `main` tiene aún el sitio antiguo en la raíz; se hace una PR inicial `develop → main` a mano, antes de activar la protección, porque `main` aún no tiene los workflows).

## Conventions

- **NUNCA JAMÁS hagas `git commit` ni `git push` de ningún cambio salvo que el usuario te lo pida explícitamente.** Trabaja siempre en el working tree y deja los cambios sin commitear. Si un cambio merece commitearse o publicarse, propónselo al usuario y espera su confirmación antes de tocar el historial o la rama remota.
- All user-facing copy is **Spanish**. Write edits in Spanish; commit messages are in Spanish too.
- Contact data lives in `content/common.yml` → `build.py` writes the contact **directly into the HTML** (`.neuro-phone`, `.neuro-mail`, `.neuro-address`, and tel/WhatsApp/mailto/Maps links) in every place it's needed, and into the generated `firma.html`. `common.yml` and `footer.yml` are read-only in Pages CMS; their address and footer text lists each require exactly two fixed items, so they cannot be added, removed, or reordered there. To change them, edit those files in the repository; the JSON-LD picks up the new phone/email/address automatically (it is generated from `common.yml` + `clinic_info.yml`). No JS is involved. Instagram lives in `content/contacto.yml` (editable from the Contact section).
- Service cards call `openServiceModal('id')` — the id is the `id` field of each item in `content/servicios.yml` (`neuro`, `psico`, `rehab`), obligatorio y editable en `.pages.yml` (minúsculas, números y guiones). Gracias a los bucles `@foreach`, `src/index.html` toma ese `id` como marcador (`__servicios.items.n.id__`), así que `data-service`/`onclick` quedan sincronizados solos; no hace falta tocarlos al añadir o quitar servicios. Modality cards call `openModalityModal(index)`; el índice lo genera el bucle con `__loop.index0__`. Blog cards call `openBlogModal(index)` y abren el artículo en un modal con su portada y el texto del campo `article`. Modal copy comes from the corresponding `SITE_DATA` collection, not from card HTML. Consultation photos are configured per modality item in `content/modalidades.yml`; the standalone gallery section no longer exists. The blog cards are real content edited in Pages CMS (`content/blog.yml`), not placeholder.
- Markers and types are the contract between the templates, `content/*.yml`, `.pages.yml` and `build.py`: every `__archivo.ruta.campo__` must exist in the YAML **and** be declared in `.pages.yml`, or the build fails. Lo mismo aplica a los marcadores de dentro de un bloque `@foreach` (p. ej. `__servicios.items.n.title__`): después de expandir el bucle se resuelven como los demás; el segmento `n` es solo el índice del elemento y no se declara en `.pages.yml`. If a field changes type in `.pages.yml` (p. ej. string → rich-text), update the marker's surrounding markup in the template (`<p>` → `<div class="markdown-content">`).
- Do not write placeholder-shaped text (`__x.y__`) in HTML comments you want to keep verbatim: the build substitutes markers **everywhere**, including comments (those are used as editor hints and end up showing the resolved value).
- No hardcoded site values: every literal that identifies this website (domain/base URL, `<html lang>`, locale, currency, logo and image paths, SEO/Open Graph/Twitter tags, menu labels, `close_label`, and the JSON-LD texts) lives in `content/clinic_info.yml` and is **read-only** in Pages CMS — edit the YAML, not `src/index.html` or `build.py`. Those two files only keep structure (markup, classes, icon names) and schema.org vocabulary (`@context`, `@type`). The only site text still in the template is the contact-card labels ("Teléfono", "Email", …) and the `&times;` close glyphs, which are part of the fixed card markup. `src/robots.txt`, `src/sitemap.xml` and `src/llms*.txt` are still static files that repeat the domain by hand.

## Verifying

- Build locally: `python build.py` (needs `pip install pyyaml markdown pillow`; sin pip se puede usar `uv run --with pyyaml --with markdown --with pillow python build.py`). Si falta Pillow y hay alguna imagen PNG/JPEG que convertir, el build se detieneindicando la dependencia., then open `_site/index.html` in a browser — never open `src/index.html` directly: its `.neuro-*` contact slots and markers are empty until `build.py` fills them.
- Lint: `prek run --all-files` (HTMLHint, Stylelint, ESLint, Lychee). Lychee has excludes for `data\.js` (generated, line too long), for source-relative assets in `src/`, for `neurogarval.es/media/` URLs until the media files are live, and for `__[a-z0-9_.]+__` template markers.
- Check section by section (`#inicio`, `#servicios`, `#modalidades`, `#proceso`, `#especialista`, `#blog`, `#faq`, `#contacto`), a service modal, each modality modal, each blog modal, and the mobile menu.
- `src/index.html` (~475 lines), `src/styles.css` (~850 lines), `src/script.js` (~75 lines); prefer targeted `Edit` calls over `Write`.
